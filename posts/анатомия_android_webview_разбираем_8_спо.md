# Анатомия Android WebView: разбираем 8 способов загрузки данных

Когда мы упаковываем статический сайт в Android-приложение (через WebView), мы сталкиваемся с суровой реальностью: **современный `fetch()` не работает для локальных файлов**.

Android WebView присваивает страницам, загруженным через `file://`, «непрозрачный источник» (opaque origin). Из-за этого браузерный движок блокирует любые попытки прочитать соседние файлы (например, наш `orcid_works.json`), считая их «чужими» из соображений безопасности.

Чтобы разобраться в этом хаосе, мы создали в приложении «Лабораторию ORCID» — интерактивный стенд с 8 методами загрузки данных. Вот подробный разбор каждого из них.

---

### 1. Fetch API (Не работает)
**Что это:** Современный стандарт загрузки данных.
**Почему не работает:** WebView блокирует запросы к `file://` из-за политики CORS. Считается, что один локальный файл не должен иметь доступ к другому.

### 2. XMLHttpRequest (XHR) (Работает)
**Что это:** Дедовский, но надежный способ.
**Почему работает:** В отличие от `fetch`, XHR в WebView имеет послабления для локальных файлов. Если в настройках WebView (`allow_file_access_from_file_urls`) разрешено чтение, XHR без проблем загружает `orcid_works.json`. Это наш «рабочий конь» для локальных данных.

### 3. Script Tag (Работает)
**Что это:** Загрузка данных через тег `<script>`. Вместо JSON мы грузим JS-файл, который просто присваивает данные глобальной переменной (`window.orcidDataJS = {...}`).
**Почему работает:** WebView не блокирует загрузку скриптов из локальной папки. Это старый-добрый JSONP-хак, который отлично работает в офлайне.

### 4. LocalStorage (Работает)
**Что это:** Кэширование данных в памяти устройства.
**Как работает:** Мы не делаем сетевой запрос. Мы просто берем данные, которые уже были загружены методами 2 или 3, и сохраняем их в `localStorage`. Это идеальный способ обеспечить мгновенную загрузку при следующем запуске приложения.

### 5. Iframe (srcdoc) (Работает)
**Что это:** Создание изолированного фрейма.
**Как работает:** Мы загружаем JSON через XHR, создаем невидимый `iframe` и «впечатываем» текст JSON внутрь него через атрибут `srcdoc`. Затем родительский скрипт читает этот текст и парсит его. Это обходит ограничения чтения файлов.

### 6. Base64 Data URI (Работает)
**Что это:** Вшивание целых страниц или данных прямо в код.
**Как работает:** Мы кодируем файл (например, английское резюме) в огромную строку Base64. Затем декодируем её в JavaScript и вставляем в `iframe` через `document.write`. Для WebView это выглядит так, будто мы сгенерировали страницу на лету — никаких запросов к файлам, никаких блокировок.

### 7. Blob URL (Fake URL) (Работает)
**Что это:** Обход CORS с помощью виртуальных файлов. (Самое интересное!)
**Как работает:** Мы читаем JSON через XHR (который разрешен). Затем создаем из этого текста виртуальный объект `Blob` (файл в памяти) и генерируем для него ссылку `blob:...`. 
Теперь мы делаем `fetch(blobUrl)`. Для WebView это выглядит как запрос к безопасному «чужому» источнику, а не к `file://`. **Fetch работает!**

### 8. Data URI Fetch (Fake URL) (Работает)
**Что это:** Еще один способ обмануть `fetch`.
**Как работает:** Мы кодируем JSON в Base64 и создаем ссылку `data:application/json;base64,...`. Затем делаем `fetch` к ней. WebView считает `data:` безопасным источником и разрешает чтение.

---

**Вывод:** Android WebView — это не сломанный браузер, а просто очень параноидальная среда. Если знать, как работают `Blob`, `XHR` и Base64, можно заставить `fetch` работать даже там, где он официально «запрещен».
